# Task 1–5: 기반과 최소 연결

모든 작업은 **미착수**다. 코드·폴더·시험명은 앞으로 만들 제안이다. 경로는 향후 Unity 프로젝트의 `Assets/MagicCampus/` 기준이며, 시험은 `Tests/<담당영역>/`, 콘텐츠는 `Content/` 아래다. 같은 단계가 모두 완료되어야 다음 단계에 착수한다. `직접 선행`은 특히 사용하는 산출물을 나타내며 이전 단계 전체 통과 규칙을 대체하지 않는다.

공통으로 [구현구조](구현구조.md), [인수기준](인수기준.md), [최신 함수 문법](../systems/full-design/11-function-syntax.md), [실행 계약](../systems/full-design/02-contracts.md)을 읽는다. 수정 범위 밖의 포트·스키마·Bootstrap 변경이 필요하면 작업을 병합하지 말고 단독 통합 작업으로 이관한다.

## 단계 1 — 기술과 계약 확정

### Task 1-1 — 실행 기반·상태·포트 계약 확정

- 직접 선행: 없음. 원본 §2·§13·§15, 기존 M0, 저장 스키마와 최종 보완을 읽는다.
- 목적/소유: 프로젝트 기준과 모든 후속 작업의 경계를 확정한다. `Contracts/`, assembly 정의, 프로젝트 설정, `Docs/ADR/`를 단독 소유한다.
- 입력→출력: 기존 JSON/스키마/함수 사전 → 지원 플랫폼·Unity/패키지 선정 ADR, 단위/타입 ID, 오류/진단, Handle/취소, 상태 DTO, 변경 계획/커밋 참가자 포트.
- 처리 구조: 순수 C#과 Unity 어댑터를 분리하고 파일·충돌·맵 로딩·시계·표시 포트를 먼저 정의한다. 기능 구현은 후속 Task에 맡긴다. 함수 핸들러는 등록형이며 임의 메서드 호출을 허용하지 않는다.
- 병렬 준비: 상태 slice별 소유자, 읽기 조회, transactionId/completionKey, definition/result 타입, perform 결과와 도메인별 커밋 검증, save migration 확장점까지 목록화한다. 미정 필드는 기본값·참조·소유자를 함께 결정한다.
- 저장/실패: 영속 normal/grant와 임시 loan scope, 전경 장면/방 활동의 복구 차이, 안전 상태 생성 포트를 확정한다. 계약에 없는 기능은 암묵적으로 구현하지 않는다.
- 완료 조건: 빈 타깃 빌드 성공, 도메인 assembly의 Unity 참조 0, 모든 후속 모듈의 포트/쓰기 영역 확정, 결정 근거와 미정 항목 목록 보존. 버전·패키지는 이 Task 결과로만 확정한다.

## 단계 2 — 서로 독립인 하부 구현

### Task 2-1 — 호출 칸 토크나이저·구문 파서

- 직접 선행: 1-1. 함수 문법과 `schemas/functions.json`, 기존 `systems/tools/parse-calls.cjs`의 정상/부정 사례를 읽는다.
- 목적/소유: `Content/Parsing/`, `Tests/Parsing/`. 콘텐츠 저작 문자열을 타입 검증 전 구문 트리로 바꾼다.
- 입력→출력: 호출 종류·문자열·파일/Pointer/엔티티 → 함수명·인자·이름표·부정·원문 범위를 가진 호출 목록 또는 진단.
- 처리 구조: 따옴표 밖 `/`와 공백만 구분한다. 허용 이스케이프, 위치/이름 인자 순서, 숫자/bool, 빈 목록, 조건의 `!`를 판정한다. offset과 1부터 시작하는 호출 번호를 보존한다.
- 경계: 함수 존재·ID 참조·가지·핸들 검증은 3-1 담당이다. 이 Task는 다른 콘텐츠 모듈을 만들거나 수정하지 않는다.
- 저장/실패: 플레이 상태 변경 0. 잘못된 입력은 진단으로 반환하며 부분 구문 트리를 실행하지 않는다.
- 완료 조건: 따옴표 안 `/`, `\"`, `\\`, 빈 when, 닫히지 않은 따옴표, 잘못된 부정/인자 순서의 기대 위치가 고정된 사례와 일치한다.

### Task 2-2 — 상태 저장소·원자 변경 계획

- 직접 선행: 1-1. 실행 계약의 권위 상태·revision·커밋 순서를 읽는다.
- 목적/소유: `State/`, `Transactions/Core/`, 해당 시험. 상태 적용의 유일한 경계를 구현한다.
- 입력→출력: 불변 조회 snapshot + expectedRevision + transactionId + 변경 계획 → 적용된 새 revision 또는 충돌/거부.
- 처리 구조: 참가자별 검증 → 변경본 구성 → 불변식 확인 → 전체 교체 → 알림 큐 순서다. 부분 적용을 피하고 동일 transactionId의 중복은 같은 결과로 종결한다.
- 경계: 도메인별 지급·성장·사건 판정은 등록 참가자가 만든다. 기반 상태 저장소가 모든 도메인의 분기를 소유하지 않는다.
- 저장/실패: 변경 전 실패는 쓰기 0, 완료/보상 원장과 상태가 함께 이동한다. 안전 저장 snapshot은 별도 확정 요청에서만 노출한다.
- 완료 조건: 두 입력의 revision 충돌, 검증 중 실패, 같은 거래 재전송에서 부분 상태·보상 중복 0. 실패한 변경 계획은 재사용하지 않는다.

### Task 2-3 — Handle·전체 임대·정지·틱 실행 기반

- 직접 선행: 1-1. 기존 architecture의 Handle/채널/틱 계약을 읽는다.
- 목적/소유: `Runtime/Handles/`, `Runtime/Control/`, `Runtime/Pause/`, `Runtime/Tick/`.
- 입력→출력: 소유자·필요 자원·취소 요청·채널 정책 → 단일 종결 Handle, 전체 임대 토큰, 채널별 실행 허용, 다음 틱 완료 큐.
- 처리 구조: Pending→Running→성공/실패/취소. 전체 자원을 정렬해 한 번에 확보하거나 0개 확보한다. 대기 우선순위는 이미 실행 중인 장면을 선점하지 않는다.
- 경계: UI·달력 구현 없이 포트와 대역으로 검사한다. 시계가 멈춰도 장면 소유 이동이 실행될 채널을 분리한다.
- 저장/실패: 토큰·Handle은 저장하지 않는다. 부모 취소는 자식 종결 후 정리하며, 중복 취소와 늦은 완료는 재종결하지 않는다.
- 완료 조건: T02–T04의 기반 모델 통과, 종결 1회·자원 누수 0·동일 입력 sequence의 순서 일정. timeout에는 정지와 독립인 감시 정책을 명시한다.

### Task 2-4 — 입력·타일맵·충돌·씬 포트 어댑터

- 직접 선행: 1-1. 원본 §2·§7, 좌표/footprint 계약을 읽는다.
- 목적/소유: `UnityAdapters/Input/`, `UnityAdapters/Maps/`, `UnityAdapters/Collision/`, 기술 시험 씬 전용 폴더.
- 입력→출력: 키보드/마우스/패드·타일맵·문 → 논리 액션, 통행 격자/portal, sweep 결과, 취소 가능한 맵 로드 결과.
- 처리 구조: 스틱 데드존·대각 정규화·UI 입력 우선 처리. 타일 좌표와 렌더 좌표를 변환하고 행위자 반경을 고려한 통과 여부를 제공한다.
- 경계: 경로 요청/도착 판정은 3-2가 담당한다. 이 단계는 플레이어 위치를 별도 시스템에서 갱신하지 않는다.
- 저장/실패: GameObject 참조 미저장. 로드 실패·취소 후 임시 씬 정리, 이전 유효 맵을 유지한다.
- 완료 조건: 8방향 입력, 좁은 문 sweep, 문 닫힘, 패드 분리, 맵 로드 실패를 실제 타깃에서 관측하고 논리 포트 결과를 확인한다.

### Task 2-5 — 파일 세대·체크섬·교체 어댑터

- 직접 선행: 1-1. 실행 계약의 SaveService·저장 예제를 읽는다.
- 목적/소유: `UnityAdapters/Storage/`, `Tests/StorageAdapter/`. 저장 정책과 분리된 디스크 작업을 제공한다.
- 입력→출력: 저장 byte payload·generation·취소 → 임시 쓰기/검증/교체 결과, 후보 정상 세대 목록.
- 처리 구조: 임시 쓰기 → 재읽기·체크섬 → 정상본 보존 → 교체. 선택 플랫폼에서 교체 원자성/지원 여부를 시험하고 보장 범위를 ADR에 남긴다.
- 경계: payload 의미·migration·안전 시점 선택은 4-2가 담당한다. 인증·계정 연동이나 클라우드 저장은 범위 밖이다.
- 저장/실패: 읽기 전용·용량 부족·취소·교체 실패에서 원본을 손상하지 않는다. 취소가 교체 이후 도착하면 실제 저장 세대를 결과로 반환한다.
- 완료 조건: 실제 임시 디렉터리에서 단계별 장애 후 최소 한 정상 세대를 읽고, 손상 파일과 다른 세대의 내용이 합쳐지지 않는다.

## 단계 3 — 검증·이동·효과·표시·시계

### Task 3-2 — 공통 이동·문·도착 서비스

- 처리 구조: 반경을 고려한 경로 → sweep 이동 → portal 검증/로드 → 목적지 거리·정지 가능성 확인. navRevision 변경과 정체는 제한 재탐색 후 명시 실패한다.
- 경계: 플레이어·NPC 일정·장면이 같은 위치 갱신 경로를 사용한다. 일반 이동 실패를 순간이동으로 바꾸지 않는다.

### Task 3-3 — 조건·효과·공유 완료키 조율

- 직접 선행: 2-2, 1-1. 02-contracts의 조건/효과와 최종 case.reward 규칙을 읽는다.
- 목적/소유: `Transactions/Conditions/`, `Transactions/Effects/`, 효과 시험.
- 입력→출력: 컴파일된 조건/효과 + 읽기 상태 + perform 결과 → 조건 설명 또는 원자 변경 계획.
- 처리 구조: 조건은 동일 revision에서 조회하고 커밋 직전 재확인한다. 완료·보상·시간·증거를 공유 completionKey와 함께 준비한다. 도메인 검증기는 등록 포트를 통해 참여한다.
- 경계: 상태 저장소를 재구현하지 않는다. 없는 도메인 효과는 성공으로 넘기지 않고 미등록 오류로 반환한다. 최소 연결에는 선언 변수·완료·기본 보상만 등록한다.
- 저장/실패: script 실패/취소 시 effects 0, 재시도 시 보상/시간 중복 0. 조율자는 변경 계획 전체를 2-2에 전달한다.
- 완료 조건: 조건 false 이유, revision 경합, 중복 완료, 일부 효과 거부에서 기대 상태가 유지된다.

### Task 3-5 — 달력·시간 비용·일 경계 서비스

- 직접 선행: 2-2, 2-3. 원본 §3·§4, 시계·자정 계약을 읽는다.
