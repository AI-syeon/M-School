01
THE BIG PICTURE

무엇을 추가하고, 무엇을 공통으로 만들까?

기획자는 누가 · 어디로 · 언제 · 무엇을 할지 적습니다. 공통 시스템은 그 내용을 읽고 이동, 대화, 상태 변경과 저장을 처리합니다.

데이터만 바꿔 추가하는 것

새 NPC, 목표 장소, 대사, 선택지, 시간 조건, 지원 함수로 조합한 사건. 예를 들어 “미라가 무대로 이동한 뒤 손을 흔들기”를 적습니다.

새 기능 개발이 필요한 것

처음 등장하는 전투 규칙, 새로운 퍼즐 원리, 새로운 조작 방식. 함수와 실패·중단·저장 규칙을 먼저 만든 뒤 데이터에서 사용합니다.

프레임워크의 목표

Unity 위에서 여러 게임에 재사용할 공통 게임 시스템을 만듭니다. 이 문서는 그 시스템의 동작 범위와 계약을 정한 기획서입니다.

이벤트 하나가 JSON 한 줄(Row)입니다. 한 행동은 한 칸 안의 함수 호출이고, 호출은 /로 이어 씁니다. 아래는 번들에 있는 event.snack의 원문이며, 다음 표는 같은 문자열을 파서가 나눈 결과입니다. 이동은 도착까지 기다리는 호출 하나로 끝나고, 결과 확정은 effects 칸이 맡습니다.

{
  "id": "event.snack",
  "category": "relationship",
  "trigger": "interact npc.serin \"간식 모임 시작\" 1.5",
  "staging": "reserved",
  "pause": "scene",
  "repeatPolicy": "once",
  "resources": [
    "npc.serin",
    "space.map.lounge",
    "input.player",
    "camera.main"
  ],
  "when": "eq story.intro_done true",
  "costMinutes": 10,
  "script": "move npc.serin dest.snack / say npc.serin \"실습 노트를 같이 정리해 볼래?\" / choice \"서린과 무엇부터 할까?\" notes \"노트부터 정리하자\" tea \"차부터 준비하자\"",
  "forks": {
    "notes": "say npc.serin \"같이 하니까 마음이 놓여.\"",
    "tea": "say npc.serin \"좋아, 따뜻한 차가 필요했어.\""
  },
  "effects": "set memory.snack_done true"
}
위치함수인자
event.snack@triggerinteractnpc.serin "간식 모임 시작" 1.5
event.snack@when#1eqstory.intro_done true
event.snack#1movenpc.serin dest.snack
event.snack#2saynpc.serin "실습 노트를 같이 정리해 볼래?"
event.snack#3choice"서린과 무엇부터 할까?" notes "노트부터 정리하자" tea "차부터 준비하자"
event.snack:notes#1saynpc.serin "같이 하니까 마음이 놓여."
event.snack:tea#1saynpc.serin "좋아, 따뜻한 차가 필요했어."

호출 위치는 event.snack#3(본문 3번째), event.snack:notes#1(가지 notes 1번째)로 부릅니다. 문법은 함수 문법 문서에 있습니다.

03

이동 결과는

도착·실패·취소를 구분합니다. 이동 실패를 도착으로 처리하거나, 평상 이동을 몰래 순간이동시키지 않습니다.

막힌 길 · 예약 합류 · 도착 판정의 세부 규칙
  • 동적 장애물로 1초간 진행이 없으면 재탐색하며 최대 3회, 기본 제한 시간은 시뮬레이션 30초입니다. 수치는 프로토타입에서 조정합니다.
  • 같은 맵에서 목표 반경 안에 있고, 충돌 없이 정지할 수 있어야 도착입니다.
  • 예약 장면만 화면 전환 또는 비관찰 공간에서 준비 지점에 안전 합류할 수 있습니다. 그다음 이동은 같은 이동기를 사용합니다.
  • 이 그림은 정적 도달 가능성을 설명합니다. 실제 움직임, 충돌, 재탐색은 Unity 구현 후 확인합니다.

WHO CONTROLS THE NPC?

서린을 두 사건이 동시에 부르면?

NPC나 장소를 쓰는 동안에는 사용권을 먼저 확보합니다. 이미 진행 중인 장면은 끝까지 유지하고, 다른 사건은 초대 목록에 남깁니다.

1주요 사건 해결 연출400
2예약 관계 장면300
3예약 행사200
4일반 상호작용100
5평상 일정10

숫자는 다음에 시작할 후보를 고르는 기준입니다. 이미 진행 중인 장면을 끊는 권한이 아닙니다.

평상 일정 중이라면

일정 이동을 멈추고, 사건에 양도

식당으로 걷는 중→일정 이동 취소→관계 장면 시작

장면이 끝나면 현재 시각을 확인하고, 현재 위치에서 새 일정 목적지로 다시 이동합니다.

관계 장면 진행 중이라면

뒤늦게 온 해결 연출은 대기

관계 장면 유지→장면 종료→다음 후보 선택

일단 시작한 장면은 강제 선점하지 않습니다. 기다린 초대는 사라지지 않습니다.

장면끼리는 순서대로, 장면 속 연출은 동시에

v1에서는 저장 상태를 바꾸는 전경 이벤트를 한 번에 하나 실행합니다. 한 장면 안에서 카메라 이동과 손 흔들기는 동시에 실행할 수 있습니다. 둘 중 하나가 실패하면 나머지도 정리한 뒤 안전 상태로 복원합니다.

SAVE & RECOVERY

장면 중 종료해도, 진행을 잃지 않게

안전 저장은 두 곳에 있습니다. 장면 진입 전과 결과 확정 후입니다. 중간 연출의 순간까지 복원하려고 하지 않습니다.

결과는 함께 확정합니다

함께한 기억, 이벤트 완료 표시, 시간 비용을 한 묶음으로 반영합니다. 기억만 생기거나 보상만 여러 번 지급되는 상태를 막습니다.

저장 실패도 알려줍니다

디스크 저장에 실패하면 이전 정상 파일을 보존하고 “완료했지만 아직 저장되지 않음”을 안내합니다. 저장 버전이 맞지 않으면 원본 파일을 유지합니다.

08
IMPLEMENTATION ORDER

먼저 만들 것은 작고 연결된 한 장면

첫 구현 목표는 “NPC와 이벤트 JSON을 추가하면 이동하고, 대화하고, 결과가 저장되는 것”입니다. 전체 게임 구현과 구분합니다.

  1. M0

    Unity 기반과 데이터 계약 고정

    버전·대상 플랫폼·파일 형식·ID·좌표·오류 표시를 정합니다.

  2. M1

    이동부터 확실하게

    같은 맵과 다른 맵 이동, 도착·실패·취소, NPC 사용권을 확인합니다.

  3. M2
    첫 연결 이정표

    JSON → 이동 → 대화 → 저장

    새 NPC·목표·이벤트를 데이터만 바꿔 추가하고, 중간 종료와 재실행까지 확인합니다.

  4. M3

    일정 · 동시성 · 진단

    시간표, 예약 큐, 병렬 연출, 미발동 이유와 장애 시험을 연결합니다.

  5. M4

    게임 고유 시스템 확장

    관계·퀘스트·물품·마법 반응·방 복구의 세부 명세와 데이터를 만듭니다.

  6. M5

    60–90분 핵심 체험

    배운 마법을 그날 쓰는 재미와 생활 부담을 실제 플레이로 확인합니다.

첫 이정표에서 꼭 확인할 것

  • 목표 좌표를 바꾸면 코드를 고치지 않아도 새 위치로 간다.
  • 실제 도착 전에는 대사가 시작되지 않는다.
  • 중간 종료 후 다시 시작할 수 있고, 완료 후 보상·시간이 중복되지 않는다.
  • 새 NPC와 새 이벤트를 JSON만 추가해 같은 규칙으로 실행한다.

식별자와 데이터 버전

정의 ID는 종류.이름 소문자 ASCII(예: npc.serin, map.courtyard)로 번들 전체에서 유일하다. 목적지는 dest.*, 문은 portal.*다. 명령에는 ID를 주지 않고 호출 위치(event.snack#3, 가지는 event.snack:notes#1)로 부른다. 기존 N01 등 원본 표기와 ID 대응은 NPC의 source 필드에 둔다. 번들 schemaVersion은 정수2(1은 이전 객체 형식이며 읽지 않는다), contentVersion은 명시 버전 문자열이다. 저장은 saveVersion·contentVersion·catalogHash를 기록한다. JSON 객체 순서는 의미가 없다. 실행 순서는 호출 칸 안의 / 순서가 정하고, 호출 칸의 문법은 함수 문법를 따른다.

정의 ID는 출시 후 재사용하지 않는다. 이름을 바꿔도 ID는 유지한다. 삭제/이동 시 마이그레이션 테이블로 치환한다. 필수 참조 누락·중복·미등록 함수·잘못된 인자·오타 필드는 번들 전체 로드를 막는다. 개발 중 유효한 이전 번들은 유지하고 오류 번들을 부분 적용하지 않는다.

좌표와 이동 계약

Position={mapId,x,y}는 타일 단위, 원점은 맵 왼쪽 위 모서리, +x 오른쪽/+y 아래, 실수 허용이다. 타일(x,y)의 중심은 (x+0.5,y+0.5). 정수 타일 인덱스와 렌더 픽셀을 섞지 않는다. 경로 노드는 타일 중심, 충돌은 반경을 포함한 연속 원/캡슐로 어댑터가 sweep한다. footprint를 통과 가능한 공간으로 팽창시킨 경로망을 사용해야 하며 단순 점 A*만으로 충돌을 보증하지 않는다. 예제는 단일 반경0.25·완전 타일 장애물이다.

목적지는 mapId·x·y·radius·facing이며 radius는 도착 허용 거리(예제0.2), 충돌 반경과 다르다. 도착은 같은 맵에서 목표 거리 이내이고 sweep상 정지 가능할 때만 성공한다. 문 통과와 도착은 별도 기록이다. 가까운 다른 칸으로 끝내고 성공 처리하지 않는다. 상호작용 목적지의 사용 대기는 목적지 점유로 처리하고 다음 NPC는 예약 대기한다.

모든 비동기 작업은 Handle{id,owner,status}를 즉시 반환한다. 상태는 Pending→Running→Succeeded|Failed|Cancelled이며 종결은 정확히 한 번이다. Result={status,code,details}. 동일 cancel을 반복해도 추가 변경이 없다. 완료 콜백은 즉시 재진입하지 않고 다음 처리 단계 큐에 넣는다. 주인은 존재하지 않는 핸들을 기다릴 수 없다. wait timeout은 자식 cancel을 요청한 후 자식 종결을 받고 자신의 실패를 반환한다.

표준 오류: DATA_INVALID, REF_NOT_FOUND, CONDITION_FALSE, RESOURCE_BUSY, NO_ROUTE, TARGET_BLOCKED, STALLED, PORTAL_CLOSED, MAP_LOAD_FAILED, TIMEOUT, CANCELLED, EFFECT_REJECTED, SAVE_INCOMPATIBLE. 취소는 실패와 구분하며 효과는 실행하지 않는다. 실패의 기본 정책은 장면 abort→마지막 안전 상태 복구→초대 유지·원인 표시다. 명시적 branch 이외에는 실패를 성공처럼 계속 진행하지 않는다.

틱 처리 순서

권장 고정 시뮬레이션 60Hz. 실제 프레임과 분리한다. 한 틱 안의 순서는 다음과 같다.

  1. 입력·전 틱 완료 신호·비동기 맵 로드 결과를 큐에 수집(안정 정렬: tick, 발급 sequence).
  2. 정지 정책을 적용하고 ClockService 게임분 누적. 경계 알림은 시간순·ID순으로 큐잉.
  3. 대기 장면 후보 조건을 같은 StateStore revision에서 판정하고 자원 전체 임대. 이미 실행 중인 장면을 강제 선점하지 않는다.
  4. 일정 재계산으로 이동 의도 생성. 이벤트 임대된 NPC는 보류한다.
  5. EventRunner는 인스턴스별 최대64개 즉시 호출 처리, 대기하는 호출(도착 대기 move, await, say 등)에서는 양보. 한도 초과는 다음 틱으로 양보하고 연속600틱 무대기 루프면 DATA_INVALID 중단.
  6. MoveService 경로 요청 처리·sweep 이동·문 전환·도착. 위치는 이 단계에서만 갱신.
  7. 효과 트랜잭션을 발급 sequence순 검증/커밋. 충돌한 revision은 조건 재검증 후 실패 또는 재평가하며 임의 덮어쓰기 금지.
  8. 종결 알림 큐잉, 해제 자원/오버레이 정리, 안전 저장 요청 스냅샷, 표시 갱신. 이번 틱 발생 신호는 다음 틱에 소비.

효과 변경이 이번 틱 앞 단계의 조건을 소급해서 바꾸지 않는다. 조건을 판정한 revision과 효과 커밋 revision을 로그에 남긴다. 동시 경합이 게임 프레임 속도에 따라 바뀌지 않게 안정 정렬한다.

시간과 정지

ClockService 권위 값은 absoluteMinute>=0. 첫날07:00=420. minuteOfDay=absoluteMinute%1440, absoluteDay=floor(/1440), 연도=floor(day/80)+1, 계절=floor((day%80)/20), 학기=floor((day%80)/40), 5일 주기=day%5. 부동 누적은 시뮬초 잔여량으로 보관하고 1초당1게임분을 기본 비율로 한다. 저장에는 정수 absoluteMinute와 0≤fraction<1만 기록한다.

정지 토큰은 세 채널로 나눈다: calendar(게임 시계), ambient(NPC 일정 이동·일반 AI), player(플레이어 조작). 대화는 calendar+player, 정식 수업/관계 장면은 calendar+ambient+player, 메뉴/전투 주문 고리는 세 채널+worldSimulation을 멈춘다. worldSimulation 중에도 UI와 취소/로드는 반응한다. 이벤트 소유 move·camera·animation은 calendar/ambient 정지 중 계속 시뮬레이션된다. 수업 장면 속 NPC도 event 소유 이동이면 허용한다. 대화 중 장면 이동을 기다려도 시계 정지와 교착하지 않는다.

실시간 wait는 pause 가능한 simulationSeconds이고 calendar와 독립이다. gameMinutes wait는 calendar에 의존하므로 calendar 정지 장면에서는 로드 오류로 금지한다(v1 wait는 simulationSeconds만 지원). costMinutes는 화면에 사전 표시하고 성공 커밋(effects 적용) 때 한 번 가산한다. 실패·취소 시 미가산. 가산으로 건너뛴 수업/행사는 경계별로 평가해 지난 회차/복습·재예약으로 표시하며 놓친 NPC 경로를 전부 재생하지 않는다.

확장 경계

이 프레임워크의 재사용 단위는 ID/카탈로그, 조건/효과, 맵/이동, 시계/예약, 명령/임대, 저장/진단이다. 게임별 adapter와 상태 모듈(전투·재배 등)은 교체한다. 전투 알고리즘, 모든 미니게임, 렌더러, 편집기, 에셋 파이프라인을 범용 엔진으로 새로 만드는 범위가 아니다. 각 함수는 지원 버전·인자 형식·핸들 결과·취소·저장 정책을 함수 사전에 등록해야 새 JSON에서 사용할 수 있다.

시스템별 실행 명세

인터페이스 표기는 C# 구현을 위한 논리 서명이며 실행 코드가 아니다. 모든 비동기 Result/Handle·오류·틱 순서는 공통 계약을 따른다. Unity 컴포넌트가 여러 곳에서 같은 상태를 변경하지 않게 한다.

1. 카탈로그와 검증

입력: UTF-8 JSON 번들, schemaVersion, 함수 사전(등록된 시작 방법·조건·명령·효과 함수). 출력: 불변 Catalog 또는 파일/JSON Pointer/오류 코드 목록. 상태: Unloaded→Parsing→Validating→Ready|Rejected. 처리: JSON 파싱→Schema→호출 문자열 파싱→함수 사전 대조(이름·인자 수·타입)→중복 ID→타입/참조→좌표·문 그래프→가지·핸들 제어흐름→효과 쓰기 충돌→자원 선언 검사→해시 생성. 기본값은 성공한 로드 후에만 정규화한다. JSON Schema의 default는 자동 삽입 기능이 아니며 별도 normalizer가 넣는다.

LoadBundle(bytes):ValidationResult<Catalog>, Resolve<T>(id):T, ExplainErrors():Diagnostic[]. 진단에는 호출 위치(call, 예 event.snack#3)와 칸 안 문자 위치(offset)가 들어간다. 작성 형식은 함수 문법. 로드 실패 시 기존 Catalog 유지. 실행 중 핫리로드 금지; 시험 모드에서 모든 이벤트 중단·임대 해제·초기 상태로 돌아간 뒤 재로드한다. Catalog는 저장하지 않고 버전·해시만 저장한다.

2. 월드·맵·목적지

입력: MapDefinition(크기·장애물·문), named destination, 상태 효과. 출력: WalkabilitySnapshot(revision), 위치, 활성 문. 상태: Unloaded→Loading→Active→Unloading; 로드 실패는 원본 맵 Active 유지. 현재 맵, 목적지 맵, 전환에 필요한 최소 맵의 논리 데이터는 유지한다. 화면 비활성 맵도 NPC 논리 위치를 소유한다. 오브젝트의 Unity 인스턴스 생성/파괴로 영속 상태를 유실하지 않는다.

GetPosition(actorId), GetDestination(id), GetNavSnapshot(mapId), SetDoorState(id,open,revision). 문은 방향성 연결이며 역방향은 별도 문 ID다. 전환은 출발 문 예약→도착 점유 검증→대상 로드→출발 맵에서 제거·목표맵 위치 등록을 한 번에 적용→전환 완료 순서. 로드 실패/도착 막힘이면 출발 문 앞 위치에 남고 실패. 양쪽 맵에 동시에 존재하지 않는다. 전환 중 save는 마지막 안전 저장을 사용한다.

임시 퍼즐 배치·전리품은 room overlay, 영구 열린 문은 StateStore 플래그에 따른 projection이다. 방 초기화는 overlay만 폐기하고 확정 증거·보상 원장을 되돌리지 않는다. 맵 재진입 시 기본 배치→영구 projection→유효 overlay 순서. 카메라 좌표·스프라이트는 영속 상태가 아니다.

3. 경로와 이동

입력: actorId, destinationId, ownerToken, timeoutSeconds(기본30), allowPortals(기본true). 출력: MoveHandle와 결과(최종 위치·경유문·재탐색 횟수). 상태: Queued→Planning→Moving↔Replanning→Transitioning→Moving→Arrived; 어느 비종결 상태에서도 Failed/Cancelled 가능.

RequestMove(MoveRequest):Handle, Cancel(handle,reason):Result, Query(handle):MoveStatus. 이벤트 move·NPC 일정·플레이어 자동 이동은 이 요청을 사용한다. 수동 플레이어 이동도 같은 sweep/충돌 실행기를 쓰되 경로 생성만 생략한다. 같은 NPC에 새 요청을 덮어쓰지 말고 먼저 임대 검사한다.

처리: 목적지/제어 토큰 검사→맵 간 방향 문 그래프 Dijkstra(문 비용+내부 예상거리)→각 구간 A*→sweep 이동→목표 도착 확인. 8방향 비용은 직선1/대각√2, 휴리스틱 octile. 동률은 y,x,문ID로 정렬. 대각선 이동은 양 직교 인접칸 모두 통과 가능해야 한다. 논리 맵 간 경로가 있어도 문까지 실제 경로가 없으면 해당 간선을 이번 요청에서 제외하고 다시 탐색한다. 무효 구간을 통과한 것으로 간주하지 않는다.

정적 충돌 변경은 navRevision을 올리고 다음 이동 전에 남은 경로를 검증한다. NPC는 동적 장애물로 sweep/점유 예약한다. 먼저 발급된 요청이 좁은 칸을 예약하고 후발은 대기. 무진행1시뮬초 후 재경로, 요청당 최대3회, 전체 timeout은 계획·대기·맵 로드 포함 시뮬시간(하드 메뉴 정지 제외). 갈 곳 자체가 없으면 NO_ROUTE, 목표 막힘은 TARGET_BLOCKED, 동적 정체 초과는 STALLED. 실패 시 마지막 유효 위치에서 정지한다. 취소는 문 전환 원자 구간 앞/뒤 경계에서 처리하고 반쯤 전환된 위치를 남기지 않는다.

경로·핸들은 임시 상태로 저장하지 않는다. 안전 복원 뒤 일정은 현재 시각에서 재요청, 장면은 진입부터 다시 시작한다. 정상 이동 실패에 자동 순간이동을 넣지 않는다. 예약 장면의 안전 합류만 별도 절차를 사용한다.

4. 시간·달력·예약·NPC 일정

입력: simulationDelta, pause tokens, costMinutes, 일정 script. 출력: MinuteCrossed/DayCrossed/AppointmentReady, NPC intent. Advance(delta), AcquirePause(channels,owner), ReleasePause(token), ScheduleAppointment(eventId,acceptedAt), RecomputeSchedule(actorId,reason).

일정은 NPC별 script 칸의 시작분 목적지 항목이다(예 420 dest.snack / 1080 home). 끝은 다음 항목의 시작(마지막은 1440)이며 구간은 반열림 [start,end), 시작분은 0–1439로 증가해야 한다. 예제는 매일 반복, 확장 필터는 weekday/weather/condition으로 추가 명세 후 지원. 같은 NPC의 일정 중복·시작분 역순은 로드 오류. 빈 구간은 home 목적지. 현재 분에 맞는 행 하나를 선택→기존 동일 목표 이동은 유지→다른 목표면 일정 이동 취소·공통 이동 재요청. 다음 일정 경계가 지나면 이전 목적지를 끝까지 방문하지 않고 현재 목표로 갱신한다. event 임대 중에는 일정 의도만 최신으로 갱신한다. 해제 시 현 위치에서 현재 목표로 간다.

예약 상태: Offered→Accepted→Ready→Running→Completed; 취소/실패는 Accepted로 돌아가며 초대 유지. 관계/행사 예약은 날짜 마감 없음. 플레이어가 수락하고 진입 조건을 만족하면 자원 임대 후 fade 또는 비관찰 공간에서 NPC를 준비 지점에 합류시키고 장면 이동을 시작한다. 눈앞의 NPC를 이동시키는 이벤트는 합류 보정 없이 현재 위치부터 이동한다. 두 방식은 콘텐츠의 staging 필드로 명시한다. 수업 종료·대량 시간 가산·로드 직후는 현재 시각 한 번으로 일정을 재계산한다. 하루 경계 작업은 (jobId,absoluteDay) 원장으로 한 번씩 처리한다.

저장: 절대 시각·fraction·Accepted 예약·일별 처리 원장·NPC 위치. 정지 토큰·현재 일정 경로는 미저장. load는 새 토큰만 만들고 과거 pause 토큰을 복원하지 않는다.

5. 조건과 효과

입력: 타입 선언 변수(예제 bool/int), 순수 Condition AST(조건 호출 문자열을 로더가 변환; /로 이은 목록은 all, !는 not), snapshot revision. 출력: bool + 이유 트리. v1 호출 eq, gte, any와 /(AND)·!(NOT); 빈 목록은 true. Evaluate(condition,snapshot):ConditionResult는 무작위·현재 화면 객체·쓰기 작업을 호출하지 않는다. 없는 변수는 false 취급 대신 REF_NOT_FOUND. eq는 선언 타입과 일치, gte는 int만. 모든 진단에 expected/actual을 남긴다.

ApplyEffects(effects,transactionId,expectedRevision):CommitResult. 예제 v1 효과는 set만, int/bool 타입 검사. 모두 먼저 검증하고 하나라도 불가하면 전체 미적용. 같은 트랜잭션에서 같은 변수 중복 쓰기 금지. event의 effects 커밋에서 효과, event 완료 키, costMinutes, 일회 보상 원장을 한 트랜잭션으로 반영한다. 이미 완료된 일회 키면 ALREADY_COMMITTED 결과로 새 효과·시간 가산 없이 성공 확인한다. 일반 이벤트 재시도와 반복 콘텐츠의 키는 다르다: once는 eventId, daily는 eventId+absoluteDay(확장), repeat는 발급된 영속 회차 ID(확장). 예제는 once만 지원한다.

조건은 행사·관계·퀘스트·상호작용·대화에서 같은 evaluator를 재사용한다. 향후 item.add, relationship.recordExperience, quest.advance 등은 타입·전제·실패·중복 키·저장 계약을 등록한 후 사용한다. 임의의 경로 문자열로 객체를 수정하는 효과나 eval은 허용하지 않는다.

6. 상호작용과 가능한 행동

입력: 플레이어 위치·대상·조건 snapshot·입력 수단. 출력: ActionView{id,label,enabled,reason,eventId} 배열. QueryActions(actor,target):ActionView[], ExecuteAction(actionId,revision):Handle. 대상 거리(타일 단위·기본1.5)·같은 맵·시선/차폐·자원 임대·이벤트 조건을 순서대로 확인. disabled도 이유와 대체 경로를 보여준다. 화면의 enabled 캐시를 신뢰하지 않고 클릭 때 재검증한다. 같은 입력 sequence는 한 번만 실행한다.

처리 상태 Idle→Focused→Requested→Running→Idle. 이벤트가 취소되면 포커스만 돌리고 카메라·입력·NPC 토큰을 회수한다. 일상 대화 중 NPC 일정 경계가 지나도 진행 중 대화는 유지하고 종료 후 재계산한다. 대화 후보는 원본 우선순위, specificity, 안정 ID순으로 선정하며 최근 동일 대사를 피하고 대안이 없으면 기본 인사 허용. 후보와 제외 이유를 기록한다. 예제 schema는 이벤트 연결 행동만 지원하며 가중 대화 선별은 M3 확장 계약이다.

7. 이벤트 실행·동시성·중단

입력: eventId·trigger context. 출력: EventHandle·trace·CommitResult. 상태: Eligible→Queued→Acquiring→Staging→Running→Committing→Completed. 조건 불충족은 시작 안 함(reason tree); 실행 중에는 명시 branch에서만 조건 재평가. 취소/명령 실패→Aborting→자식 cancel/종결 확인→오버레이·UI 정리→토큰 해제→진입 안전 상태 복원→Accepted 재등록. commit 성공 후 cancel은 TOO_LATE로 완료를 유지한다.

TryStart(eventId,context):StartResult, CancelEvent(instanceId,reason), ExplainEligibility(eventId):ReasonTree. scene 자원은 npc.*, space.map.*, input.player, camera.main으로 명시. 모든 쓰기 자원을 시작 전에 원자 임대하며 실패하면 아무것도 잡지 않고 대기한다. 공통 우선순위: 해결 연출400 > 관계300 > 행사200 > 일반 상호작용100 > 일정10. 같은 우선순위는 예약 시각·sequence·eventId순. 실행 중 장면은 강제 선점하지 않는다. 생존/자정 귀환은 새 장면이 아니라 안전 중단 요청이며 현재 원자 커밋/전환 종료 뒤 처리한다. 대기30시뮬초마다 RESOURCE_BUSY 진단, 초대 자체 만료 없음. 장소가 겹치지 않아도 대화창 하나·카메라 하나면 동시 임대 불가.

일정은 장면과 달리 선점 가능하다. 높은 우선 장면이 NPC를 요구하면 ControlService는 해당 일정 move를 취소 요청하고 종결 확인 뒤 일정 임대를 해제한다. 장면은 기다리는 동안 다른 자원을 부분 점유하지 않는다. 그 뒤 전체 자원을 다시 원자 획득한다. 실행 중 장면 간 선점 금지 규칙 때문에 평상 일정이 새 장면 시작을 영원히 막지 않도록 구분한다.

v1은 effects를 커밋하는 모든 이벤트(v1 이벤트 전부)에 암묵적 전역 안전 저장 임대(snapshot.world)를 추가한다(JSON resources에 작성하지 않음). 따라서 장소가 달라도 영속 효과를 가진 전경 장면은 하나만 Running이다. 동시 후보는 큐에서 보존한다. 병렬은 그 장면 안의 async=+await 연출과 상태를 쓰지 않는 순수 배경 표시만 허용한다. 방 일별 처리·별도 보상 등 외부 영속 효과는 장면 동안 큐에 두고 완료/복원 후 처리한다. 전체 진입 스냅샷을 복원하면서 다른 이벤트의 완료를 지우는 문제를 막는 제한이다. 향후 독립 영속 이벤트 동시 실행이 필요하면 전체 롤백을 범위별 트랜잭션으로 바꾸고 별도 버전으로 설계해야 한다.

순차 호출은 앞 호출 성공 후 다음 실행. move는 기본으로 도착까지 대기한다. async=핸들을 주면 작업을 시작해 핸들을 남기고 바로 다음 호출로 가며, await가 성공까지 대기한다. 닫히지 않은 핸들·없는 핸들·중복 이름은 로드 오류. 실패/취소 결과는 기본 abort로 전파한다. branch는 순수 조건으로 고른 가지(forks)만 실행. 연이은 async= 호출은 같은 snapshot에서 시작하고 await가 전부 성공해야 진행(join=all). 한 호출 실패/취소면 나머지 cancel→종결 후 이벤트 실패. v1 join=any와 분리 실행(await 없이 끝내는 async)은 미지원. 동일 actor·카메라를 쓰는 async 충돌은 로드 오류(HANDLE_CONFLICT). 핸들은 가지로 넘기지 않으며 가지 호출은 부모 자원 부분집합만 쓰므로 교착을 막는다.

커밋은 effects 칸이 정확히 한 번 한다(script 성공 뒤). 장면 중 영속 효과 금지, 선택 결과는 local(예제 선택별 가지)로 분기하고 마지막 효과를 effects에 모은다. 효과 함수는 명령 사전에 없으므로 가지 안에 효과를 숨기거나 병렬 커밋을 만들 수 없다. checkpoint는 장면 진입·완료만 v1 지원. 중간 PC·대사 글자·경로 재개는 지원하지 않는다. 스킵은 UI/애니메이션만 가속하고 이동 성공·선택·효과를 생략하지 않는다.

8. 대화·선택·카메라·애니메이션·입력

입력은 호출 say 화자 "대사", choice "질문" 가지 "선택문"…, camera 목적지 초, animate 행위자 클립 초. 출력은 각 Handle의 완료·실패·취소. 대사는 마지막 글자 표시 후 확인 입력으로 완료; 글자 빨리 표시는 완료와 구분. choice는 enabled 옵션 최소1개, 선택은 한번 확정 후 해당 가지(forks)의 호출목록 순차 실행. 취소 버튼은 전체 event cancel(원본 상태 복원), 뒤로가기 중 보상 지급 없음.

카메라는 논리 목적지를 엔진 좌표로 변환하고 제한 영역 안으로 clamp. 애니메이션 clip은 adapter 등록 키며 미등록이면 로드 실패, 종료 신호 누락이면 duration+허용오차 후 TIMEOUT. duration은 데이터 양수. 완료/실패/중단 모든 경로에서 이벤트가 잡은 입력·카메라 토큰을 finally로 회수한다. 이전 카메라 모드와 입력 map을 저장한 임대 스택으로 되돌리고, 다른 이벤트 토큰을 해제하지 않는다. Presentation 상태는 안전 저장에 포함하지 않는다. 예제는 text만 있고 실제 폰트/초상/애니메이션 파일을 제공하지 않는다.

9. 저장·복원·버전

RequestSave(slot):SaveResult, Load(slot):LoadResult, Migrate(snapshot,target):MigrationResult. 상태 Idle→Snapshotting→WritingTemp→Verifying→Replacing→Idle; 실패면 Failed와 이전 정상 파일 유지. Snapshot은 틱 경계의 불변 복사. 동시 요청은 직렬화한다. 저장 파일에는 저장 버전·콘텐츠 버전/해시·세대·시계·위치·선언 상태·완료 키·예약·방 체크포인트가 들어간다. 체크섬은 파일 envelope에서 canonical payload 바이트에 적용하며 예제는 envelope 전 payload다.

진입 절차: 조건/자원 확인·전체 임대→NPC 합류 이전 월드와 예약 포함 안전 스냅샷 확정→scene overlay 생성→staging. snapshot.world는 완료 후 불변 스냅샷 확보 또는 abort 복원까지 유지한다. 취소 정리·복원은 하나의 틱 경계 작업으로 수행하고 그 사이 새 이벤트/일정을 실행하지 않는다. 중간 수동 저장 요청은 마지막 안전 스냅샷을 해당 슬롯에 쓰고 “현재 장면은 시작부터 다시 진행”을 안내한다. 종료 후 로드는 그 스냅샷에서 Accepted 예약을 복원한다. 자동 시작 중복을 막고 플레이어가 다시 시작하게 한다.

완료 절차: 효과·완료·시각을 메모리에서 원자 반영→오버레이와 토큰 정리→완료 후 안전 스냅샷 쓰기→성공 안내. 디스크 실패면 “완료·미저장” 상태로 재시도 UI를 제공하며 이전 정상 파일을 보존한다. 이때 세션 내 원장이 중복 커밋을 막는다. 강제 종료로 이전 저장을 불러오면 완료 전 상태 전체를 복원하므로 보상만 따로 남지 않는다. 보상 지급을 외부 서버나 별도 파일에 분리하지 않는다.

로드 순서: envelope/체크섬→saveVersion→catalog version/hash→연속 마이그레이션→Schema/참조/불변식→서비스 임시 인스턴스 구성→전체 교체→projection/일정 재계산. 마이그레이션 불가한 미래 버전·누락 필수 맵은 SAVE_INCOMPATIBLE, 원본 슬롯 보존. 선택 장식 제거는 명시 migration에서 우편 대체 가능. 기존 hash와 다른데 migration이 없으면 임의 로드 금지. v1→v2가 아직 정의되지 않았으므로 이번 예제는 버전1 동일 카탈로그만 유효하다.

10. 인벤토리·관계·퀘스트·생활·전투의 경계

11. Unity 적용 책임

순수 C# 도메인 서비스는 MonoBehaviour·Transform·씬 인스턴스 ID에 의존하지 않게 설계한다. Unity 쪽은 WorldView(표시), InputAdapter, CollisionAdapter, MapLoader, DialogueView, CameraAdapter, AnimationAdapter, FileStore로 나눈다. 논리 mapId와 Unity 씬/프리팹 연결은 별도 asset binding으로 둔다. Transform은 도메인 위치의 표시 결과다. 이벤트 명령마다 새 MonoBehaviour를 만들거나 NPC별 스크립트를 복사하지 않는다.

중앙 GameLoop가 공통 틱 순서를 호출한다. Unity의 서로 다른 컴포넌트 갱신 순서에 우연히 의존하지 않는다. 맵 로드/애니메이션 콜백은 도메인 큐로 반환한다. 에셋 없는 상태에서도 임시 도형·텍스트로 인수 시험이 가능해야 한다. Unity 버전·패키지 API 선택은 이번 기획에서 확정하지 않으며 Unity 프로젝트 생성이나 플레이 실행은 수행하지 않았다.

콘텐츠 작성과 데이터 계약

2026-11-02 작성 형식 변경: 한 행동은 한 칸의 함수 호출, 한 이벤트는 JSON Row 하나(스타듀밸리 방식). 문법과 결정은 함수 문법이 정한다. 이 문서는 v1 공통 기반이 쓰는 함수 범위를 적는다. 실행·임대·저장·커밋 계약은 바뀌지 않았다.

지원 범위

v1 스키마는 이 명세의 최소 연결 예제를 위한 범위다. 맵·NPC·일정·조건·이벤트·기본 안전 저장 payload를 지원한다. 상호작용은 이벤트의 trigger 칸이 대신하므로 별도 표가 없다. 전체 출시 콘텐츠의 재배/전투/레시피/관계 집합/퀘스트 데이터 스키마는 아직 만들지 않았다. 시스템 설계의 확장 계약과 실제 스키마 지원을 구분한다. 향후 확장은 스키마 버전 또는 함수 사전에 함수를 등록해서 추가한다.

JSON Schema Draft 2020-12 문서이며 스키마는 칸의 모양(문자열인지, 필수인지)만 본다. 호출 문법·함수 이름·인자·참조의 실제 존재·중복 ID·경로·핸들 순서는 별도 의미 검사가 한다. 번들 내부에 $defs를 묶어 네트워크 없이 사용한다. 제공 검증기는 이 두 스키마에서 사용하는 키워드만 해석하는 작은 문서 검사 도구다. 범용 JSON Schema 구현이나 Unity 런타임이 아니다. Unity 구현 단계에는 표준 스키마 검증기와 계약 테스트를 선정하고 같은 예제/부정 사례를 실행해야 한다.

호출 문법

모든 호출 칸(trigger·when·script·forks·effects·일정 script)이 같은 규칙을 쓴다. 전체 문법은 함수 문법에 있고 파서는 tools/parse-calls.cjs 한 곳이다.

호출목록 := 호출 ( "/" 호출 )*        빈 문자열 = 호출 0개
호출     := [이름표 ":"] ["!"] 함수이름 인자*
인자     := 위치인자 | 키 "=" 값
  • /는 호출을, 공백은 인자를 나눈다. 공백·/·=·:가 든 글은 큰따옴표로 감싸고 \"와 \\만 이스케이프한다.
  • 위치 인자가 먼저, 키=값이 뒤에 온다. 생략한 인자는 함수 사전의 기본값을 쓴다.
  • !는 조건 함수에만 쓴다. 함수 이름은 등록된 이름만 허용한다. eval·임의 메서드 호출은 없다.
  • 로더는 문자열을 기존과 같은 타입 객체로 바꾼다. 실행기는 그 객체만 다루므로 실행·임대·저장 계약은 그대로다.

핸들과 가지 규칙

핸들 규칙은 이전과 같고 표기만 바뀌었다.

  • async 핸들은 같은 호출목록(script 또는 한 가지) 안에서 await로 닫는다. 닫지 않은 핸들이 있으면 say·choice·branch와 목록 끝을 거부한다(HANDLE_UNAWAITED).
  • 핸들은 가지로 넘기지 않는다. 가지 안의 await가 바깥 핸들을 부르면 HANDLE_UNDEFINED다. 핸들 이름은 한 목록에서 한 번만 쓴다(HANDLE_DUPLICATE).
  • 열려 있는 async가 쓰는 행위자·카메라를 같은 목록의 다른 호출이 쓰면 오류다(HANDLE_CONFLICT). 대화창은 say·choice가 열린 핸들을 거부하므로 겹칠 수 없다.
  • 가지 이름은 같은 Row의 forks에 있어야 한다(FORK_NOT_FOUND). 어디서도 부르지 않는 가지는 FORK_UNUSED, 서로 부르는 순환은 FORK_CYCLE다.
  • 효과는 effects 칸에만 있으므로 병렬 쓰기 충돌을 런타임 임의 승자로 해결하지 않는다.

플레이어는 오래된 마법학교의 신입생이다. 아침에는 오늘 들을 수업과 만날 친구를 고르고, 오후에는 배운 주문으로 학교와 주변을 탐험한다. 저녁에는 기숙사에서 친구들과 시간을 보내거나, 재료를 실험하고 방을 꾸민다. 학교 곳곳의 이상 현상을 해결하다 보면 학교를 지탱하는 마법과 과거의 선택을 알게 된다. 어떤 사건부터 해결할지는 플레이어가 고른다.

추천 방향은 학교생활 중심의 싱글플레이 생활 RPG다. 전투, 제작, 재배, 탐험은 학생의 생활과 연결한다. 넓은 세계나 많은 직업보다, 자주 오가는 장소와 사람의 변화를 깊게 만든다.

기본 시계는 게임 내 10분당 현실 10초다. 하루 17시간을 모두 필드에서 보내면 현실 약 17분이다. 대화·메뉴·정식 수업·관계 장면·퍼즐 배치 화면에서는 시계를 멈추고, 완료 시 표시된 게임 시간을 더한다. 따라서 실제 하루 플레이는 장면을 포함해 대략 20–35분으로 달라진다. 달력 일수만으로 40시간을 계산하지 않는다.

수업은 시작 전 알림이 오며 교실 앞에서 참여할 수 있다. 늦으면 다음 회차나 실습실의 복습을 선택한다. 수업을 시작하면 친구의 진행과 플레이어의 진도가 맞도록 해당 수업용 장면으로 전환한다. 수업 중 NPC의 월드 이동은 멈추고 종료 후 일정을 재계산한다.

탐험 구역에서도 시계는 흐른다. 퍼즐 조작과 대화는 일시정지한다. 안전지점에서 귀환할 수 있고, 입구에는 예상 소요 시간과 다음 안전지점이 표시된다. 늦은 출발은 막지 않되 자정 귀환 규칙을 미리 안내한다.

자정에는 귀환 알림 후 안전한 상태에서 기숙사로 이동한다. 퀘스트 아이템과 확정 해금은 보존한다. 진행 중 퍼즐은 해당 방의 입장 상태로 복원하고 이전 방의 완료는 유지한다. 전투 중에는 경고 후 귀환을 선택하거나, 현재 교전을 끝내고 귀환한다. 자정을 넘긴 추가 전투는 새로 발생하지 않는다. 이 규칙은 무한 시간 활용과 진행 유실을 함께 막는다.

4. 학교생활과 성장

시간표와 출석

주 5일 주기를 사용한다. 정규 수업 3일, 공동 실습 1일, 자유 활동 1일을 기본으로 하고 세부 과목은 시간표에서 고른다. 휴일에도 교정·기숙사·실습실은 열려 있다. 정상적인 학교 분위기를 위해 종, 식사 시간, 교실 이동, 같은 반 학생들의 일정을 표현한다.

출석하면 동급생과 함께 배우는 짧은 대화, 재료 지원, 실습 효율을 얻는다. 결석으로 주문·메인 사건·학년 수료를 영구 차단하지 않는다. 필수 능력은 실습실에서 교재와 대여 도구로 배울 수 있다. 해당 수업의 인물 장면도 복습 모임으로 다시 볼 수 있다. 재료 지원은 회차별 중복 수령이 불가능하다.

성적과 성장

성장은 주문 습득, 주문별 응용, 실습 기록, 관계 변화, 생활 공간 개선으로 나눈다. 전역 캐릭터 레벨과 적 레벨의 경쟁을 핵심으로 삼지 않는다. 실습 기록은 과제를 어느 방식으로 풀었는지 남기며, 잘못 풀어도 피드백 후 다시 시도할 수 있다. 최고 점수는 선택 목표다.

주문 응용은 반복 시전 횟수가 아니라 서로 다른 상황 3개에서의 사용으로 해금한다. 부유라면 가구 배치·공연 소품 고정·탐험 무게추 조절만으로도 충분하다. 투사체를 다루는 전투 활용도 인정하지만 전투를 필수로 하지 않는다. 부족한 상황은 복습실의 서로 다른 과제로 보충할 수 있다. 이미 사용한 상황을 계속 반복해도 진행 점수를 주지 않는다. 응용 변경은 기숙사에서 무료다. 응용 해금과 수업의 응용 실습은 별개이며, 응용 실습은 해당 기초 수업만 요구하고 주문 응용 해금을 선행 조건으로 삼지 않는다.

학교의 압박 수준

학교는 규칙이 있는 공동체다. 위험 구역에 들어가면 경고를 듣고, 공용 실습 도구를 망가뜨리면 함께 고치는 짧은 후속 행동이 생긴다. 벌점 누적으로 퇴학하거나 스토리가 막히지는 않는다. 수업·통금의 규칙은 분위기와 선택의 결과를 만들고, 현실의 출석 스트레스를 재현하는 장치로 쓰지 않는다.

5. 마법: 같은 주문으로 생활과 모험을 연결

기본 조준은 가까운 상호작용 대상을 선택하는 방식이다. 전투에서는 방향 조준과 보조 조준을 지원한다. 주문 4개를 빠른 슬롯에 놓고, 안전한 순간에는 주문 고리에서 교체한다. 전투 중 주문 고리를 열면 게임 전체가 일시정지한다. 탐험을 나가기 전 정답 주문을 장착하지 않았다는 이유로 돌아오게 만들지 않는다.

일상 시전에는 마나를 소모하지 않는다. 전투에서는 집중력 100을 쓰고 교전 종료 후 회복한다. 집중력이 없을 때도 기초 마력탄과 회피, 환경 장치 사용은 가능하다. 생활 마법을 계속 쓰고 싶어도 전투 자원을 아끼느라 참는 상황을 피한다. 마법 효과는 대상의 성질로 결정한다. 사람·사유물에는 임의의 파괴·강제 조작을 허용하지 않고 상호작용 가능한 대상임을 미리 표시한다.

조합은 제한된 규칙으로 만든다

물결+서리는 젖은 표면을 얼린다. 돌풍+메아리는 소리의 방향을 바꾼다. 부유+결계는 움직이는 물체를 정지시킨다. 싹틔움+불씨는 건조한 씨앗 껍질을 열되 살아 있는 작물을 태우지는 않는다. 자유 조합 전체를 구현하지 않고, 눈에 보이는 성질과 도감에 기록된 조합 6종을 우선 만든다. 나머지 두 조합은 등불+환영의 기록 투사, 수선+돌다듬기의 구조물 복구다.

잘못된 주문을 쓰면 짧은 반응과 관찰 정보가 나오며 필수 재료를 잃지 않는다. 불씨가 반응하지 않는 봉인은 “열에는 반응하지 않는다”는 정보가 남는다. 시행착오는 정답을 외우는 비용보다 세계를 이해하는 과정이 되어야 한다.

12개 주문마다 기초 실습 1개와 응용 실습 1개를 제작한다. 도입에서 배우는 등불·부유의 기초 실습 2개는 도입 시간에만 산정한다. 정식 수업 시간 예산에는 남은 22개를 넣는다. 기초 실습은 하나의 원리를 보여주고, 응용 실습은 생활 또는 탐험 문제를 두 방법으로 해결한다. 같은 조작을 반복하는 10단계 시험으로 늘리지 않는다.

도입 후 초급 M03–M06의 기초 수업을 모두 선택할 수 있다. 초급 기초를 서로 다른 두 과목 완료하면 중급 M07–M10을, 중급 기초 두 과목 완료하면 응용 M11–M12를 선택할 수 있다. 정규 수업과 복습은 같은 완료 기록을 사용한다. 날짜를 기다리는 조건은 없고, 원하는 순서로 더 빨리 배울 수 있다. 각 주문의 응용 실습은 해당 기초만 요구한다. 일반 플레이에서는 2시간에 2개, 6시간 전후에 6개, 12–16시간에 12개를 경험하는 것을 목표로 안내하되 강제로 시간을 검사하지 않는다. 나머지 분량에서는 주문 조합·장면의 재해석·관계·학교 변화가 성장을 담당한다.

개인 화분 6칸과 공동 온실 12칸을 기본으로 한다. 식물은 약초 4종, 생활 재료 4종, 특이 반응 식물 4종으로 총 12종이다. 성장 기간은 기본 2–4일이다. 계절은 수확 보너스와 외형에 영향을 주고, 필수 식물을 특정 계절에만 얻을 수 있게 만들지 않는다. 온실에서 모든 필수종을 소량 재배할 수 있다.

매일 물주기를 놓쳐도 식물이 죽지 않고 성장이 잠시 멈춘다. 싹틔움은 시간을 무한히 건너뛰는 수익 수단이 아니라 잎·꽃·씨앗 중 수확 부위를 선택하는 마법이다. 화분 자동 급수는 초반 생활 프로젝트로 제공한다. 재배에 관심이 없으면 학교 지급 재료나 상점으로 핵심 제작을 진행할 수 있다.

7. 전투와 탐험

전투의 기본

목표는 빠른 손놀림만 요구하는 액션보다 적의 행동을 관찰하고 배운 주문을 적용하는 짧은 교전이다. 공격·주문·회피·상호작용이 기본 조작이다. 적은 공격 전에 방향과 범위를 표시한다. 일반 교전은 30–90초, 큰 교전은 3–5분을 시작 목표로 한다. 한 화면에 동시에 공격을 준비하는 적은 기본 3체 이하다.

기초 마력탄에는 자원 비용이 없다. 강한 주문에는 집중력 10–30을 쓰고, 교전 종료 후에는 전부 회복한다. 교전 중 2초 동안 피해를 받지 않으면 초당 5씩 자연 회복하고, 환경 목표를 해결하면 10을 추가 회복하는 것을 시작값으로 한다. 빈 집중력 때문에 아무 행동도 할 수 없는 상태는 없다. 회피에는 짧은 재사용 대기시간을 두고 무한 연타로 모든 공격을 무시할 수 없게 한다.

난이도와 패배

기본·편안함·도전의 세 프리셋을 제공하고 피해량, 조준 보조, 공격 예고 길이를 개별 조절할 수 있다. 편안함은 적 피해 50%, 예고 시간 150%를 시작값으로 한다. 3회 패배하면 지원 부적과 장치 해결 힌트를 제안한다. 사용 여부는 보상·관계·엔딩의 등급을 깎지 않는다. 설정은 언제든 바꿀 수 있다.

패배하면 마지막 안전지점으로 돌아가며 확정한 보상·단서·열린 문은 유지한다. 현재 방의 적과 퍼즐만 재설정한다. 돈·가구·필수품은 잃지 않는다. 중복 회수로 재료를 복제하지 않도록 해당 방에서 얻은 미확정 전리품만 되돌린다. 재도전 시 설명과 컷신을 건너뛸 수 있다.

생활 중심 유저도 약한 적과 마법의 반응을 경험하게 하되, 주요 사건에는 전투 실력이 부족할 때 장치·준비·지원으로 완료할 경로를 둔다. 모든 일반 적을 위한 별도 대화 시나리오는 만들지 않는다. 큰 사건의 갈등을 해결하는 대체 경로만 수작업으로 만든다.

관계의 진행

관계 단계는 얼굴을 아는 사이→함께하는 사이→사정을 아는 사이→신뢰하는 사이로 표현한다. 내부 친밀도는 0–100을 사용하되 수치보다 최근 함께한 활동과 다음 초대 조건을 보여준다. 첫 관계 사건은 인사와 활동 한 번으로 열리고, 두 번째는 첫 사건 완료와 다른 공동 활동 두 번, 세 번째는 두 번째 완료와 각 인물의 후속 부탁으로 연다. 하루별 호감도 작업을 여러 번 반복해야 하는 구조를 피한다.

관계 준비의 공동 활동은 이미 목록에 있는 수업·부탁·프로젝트·동아리·식사를 활용한다. 한 활동에 같이 참여한 인물이 여러 명이면 각자의 경험에 함께 기록한다. 관계 해금을 위해 별도의 미집계 미니 퀘스트를 추가하지 않는다. 세 번째 사건의 후속 부탁은 해당 R03·R06 등 사건 안의 준비 행동이며 평균 9분에 포함한다. 조건을 하루에 연속 충족해도 강제 대기일 없이 다음 초대가 등록된다.

서로 다른 공동 활동은 한 종류당 첫 수행 +8, 평범한 새 대화는 하루 +2, 선물은 하루 +2 정도를 시작값으로 삼는다. 다음 관계 사건을 보기 위한 필수 조건은 위 공동 경험이며, 숫자만 쌓아서 사건을 건너뛰지는 못한다. 반대로 주요 사건 협조·공공 정보·필수 대여품은 관계 수치를 요구하지 않는다.

같은 선물 반복으로 관계를 끝내지 못하게 하되 선물 행위 자체를 처벌하지 않는다. 좋아하는 것을 게임 내 대화와 관찰로 알 수 있다. 장기간 만나지 않았다는 이유로 관계가 내려가지 않는다. 갈등 대화는 잠깐의 반응을 바꾸고 수첩에 화해 행동을 제시하며, 필수 콘텐츠를 없애지 않는다.

학생 6명은 세 번째 관계 사건에서 친밀한 우정 또는 연애를 선택할 수 있게 한다. 성인 학생끼리만 가능하며, 교직원과 주민은 우정 관계다. 연애는 같은 사건의 마지막 대화·포즈·호칭을 바꾸는 범위로 제한한다. 별도 결혼·가족·동거 시스템은 최초 범위에서 제외한다. 연애를 선택하지 않아도 관계 서사와 보상은 완결된다.

대화와 동행

각 주요 NPC에 기본 일상 대화 24묶음과 상황 반응 12묶음을 우선 제작한다. 기본 대화는 시기·장소·최근 활동에 맞춰 고르고, 같은 내용을 연속 재생하지 않는다. 상황 반응은 사건 해결, 공동 프로젝트, 관계 사건 후 변화에 연결한다. 모든 사건×모든 관계 단계×모든 날씨 조합의 전용 대사를 만들지 않는다. 특별 반응→관계 후일담→장소·시기 대화→기본 인사의 우선순위로 충돌을 줄인다.

학생 6명에게 하루 한 번 동행을 신청할 수 있다. 길찾기 부담을 줄이기 위해 동행은 지정 거점 사이에서 순간 합류하고, 좁은 길에서는 뒤따르기보다 장면용 위치로 이동한다. 각자의 도움은 수리 시간 단축·안전 힌트·생활 수확 보조 등 편의다. 동행 없이도 모든 필수 사건을 해결할 수 있다. 복잡한 자유 전투 AI 동료는 초기 범위에서 제외하고 사건의 지정 지점에서 도움을 주는 방식으로 만든다.

NPC 위치는 수첩에 현재 생활 구역과 다음 일정으로 표시한다. 관계 사건은 조건 충족 시 우편 초대로 등록되고, 플레이어가 수락하면 장소에서 예약 장면을 시작한다. NPC가 비 오는 날 다른 장소로 갔다는 이유로 여러 날 찾게 만들지 않는다. 예약되지 않은 일상 만남은 실제 일정대로 표현한다.

9. 전체 이야기와 자유 순서 사건망

이야기의 중심 질문

학교를 보호하던 공명핵이 학생들의 새 주문과 생활 변화를 오류로 판단하기 시작했다. 물길, 온실, 서가, 관측 장치, 공연 환영, 안전 결계가 각각 다른 소동을 일으킨다. 처음에는 별개의 고장처럼 보이지만, 조사하면 오래전 비상 운전 방식이 그대로 남아 있다는 사실을 알게 된다.

플레이어는 선택받은 구원자가 아니라, 친구들과 서로 다른 문제를 연결하는 신입생이다. 교직원은 무능해서 일을 맡기는 것이 아니라 기본 안전과 핵심 장치를 지키고 있다. 학생들은 소규모 현장 조사와 새로운 응용을 담당한다. 위험한 마지막 작업에는 학교 전체가 참여한다.

이야기의 질문은 “모든 변화를 막아 안전을 유지할 것인가, 변화를 받아들이며 관리할 것인가”다. 따뜻한 생활이 기본 분위기이며 잔혹한 희생이나 영구적인 NPC 사망을 반전의 동력으로 쓰지 않는다.

6개 사건은 도입 이후 모두 ‘발견 가능한 상태’가 된다. 첫 화면에는 가까운 두 사건만 자연스럽게 소개하고, 게시판의 소문·NPC 대화·직접 방문으로 나머지를 찾는다. 원하면 수첩의 전체 소문 목록을 바로 열 수 있다. 자유를 주기 위해 처음부터 18개 목표를 화면에 쌓지는 않는다.

각 사건은 발견·조사·해결의 3개 노드로 구성한다. 한 사건 안의 1→2→3 인과는 고정하고, 서로 다른 사건 사이에는 선행 사건 조건을 두지 않는다. 필요한 주문을 배우지 않았으면 대여 도구와 현장 조작으로 같은 상태에 도달한다. 다른 사건에서 얻은 지식이나 동행이 있으면 해결의 설명과 편의를 바꾸고 입장 가능 여부는 바꾸지 않는다.

2개 해결 시 중간 정리 A, 4개 해결 시 중간 정리 B를 열어 단서를 연결한다. 두 장면은 새로운 필수 능력을 지급하지 않으며 플레이어의 수첩에서 언제든 다시 읽는다. 6개를 해결하면 최종 실습 준비가 완료된다. 특정 학기·NPC 친밀도·수업 성적·수집률을 추가로 요구하지 않는다.

도구는 필수 통과를 보장하고 주문은 더 직접적인 조작과 응용의 만족을 준다. 대여대를 찾는 시간이 새 장애물이 되지 않게 입장 안내와 수첩에 표시한다. 이는 문서 수준의 경로 명세이며 실제로 통과 가능한지는 구현 후 시험한다.

어떤 순서로 해도 이해되는 정보

각 사건은 “현장 사실 하나 + 학교 전체에 대한 증거 하나”로 끝난다. 어느 사건에서도 다른 사건의 인물을 이미 만났다고 가정하지 않는다. 인물 소개는 첫 등장 여부를 확인하고 한 번만 재생한다. 진실 정리 A는 발견한 증거로 문제의 공통 원인을 정리하고, B는 해결 가능한 설계를 제시한다. 미발견 사건의 정답을 먼저 공개하지 않는다.

예를 들어 C를 먼저 끝내면 “갱신 절차가 있었는데 왜 멈췄을까?”가 질문이 된다. D를 먼저 끝내면 “누가 비상 운전을 끝내지 않았을까?”가 질문이 된다. 어느 경우든 모든 증거가 모이면 동일한 사실을 이해하고, 중간 대사의 질문만 달라진다. 수백 개의 전체 순서별 스크립트 대신 증거 보유 여부에 따른 짧은 연결 문장을 사용한다.

단서를 의뢰 전에 얻었으면 이미 발견한 것으로 인정한다. 해당 사건을 수락한 순간 수첩에 기존 기록이 합쳐지고, NPC는 “이미 살펴봤구나”라고 반응한다. 아직 해결하지 않은 현장을 해결했다고 말하는 대사는 완료 플래그가 있을 때만 재생한다.

상세 사건 예시: A3 물길 복구

  1. 입구에서 뜨거운 배관과 식당으로 이어진 표식을 확인한다. 안전 거점과 귀환문을 등록한다.
  2. 소형 수조에서 물결로 수위를 바꿔 본다. 주문이 없으면 대여 물병 또는 수동 펌프가 같은 역할을 한다.
  3. 주실에서 과열 인형이 물길을 잘못 막고 있음을 발견한다. 전투 해결과 장치 해결 중 하나를 고른다.
  4. 전투 경로는 돌진 예고를 피하고 물결·서리·환경 물통으로 인형을 냉각한 뒤 정지시킨다. 장치 경로는 옆 유지보수 통로에서 밸브 2개와 결계를 조작해 공급을 차단한다. 두 경로는 인형 정지 상태로 합류한다.
  5. 수선 주문 또는 대여 공구로 명령 부품을 복구한다. 중앙 명령의 오류 기록을 얻는다. 적을 파괴해야만 기록을 얻는 구조가 아니다.
  6. 식당에 돌아오면 분수가 작동하고 점심 메뉴의 짧은 반응이 바뀐다. 친구의 별도 관계 사건이 있다면 다음 날 초대가 올 수 있지만 사건 완료 조건은 아니다.

장치 경로가 항상 더 쉽고 빠르면 전투가 형식적인 선택이 된다. 두 경로의 목표 시간은 6–8분으로 비슷하게 맞추고, 전투는 반응·조합, 장치는 관찰·공간 이해를 요구한다. 난이도 설정은 각 경로에서 별도로 도움을 준다.

최종 실습과 엔딩

6개 사건의 복구 기록을 바탕으로 학교가 최종 작업을 준비한다. 교정의 준비 게시판에서 “아직 생활하기” 또는 “최종 실습 시작”을 고른다. 미완료 관계 사건·행사·프로젝트 목록을 보여주고, 계속하기가 가능하다고 명시한다. 시작 전에 별도 보관 저장을 만든다.

마지막 작업은 세 구간의 공명 흐름을 조정하고, 마지막 중심 장치에서 전투 또는 안정화 퍼즐을 수행하는 구조다. 학생과 교직원은 이미 해결한 영역을 맡는다. 특정 친구와 친하지 않으면 그 역할을 교직원이 맡고, 관계가 좋으면 친구의 개인 대사가 추가된다. 준비 비용이나 희귀 재료는 요구하지 않는다.

마지막 선택은 감독하에 중심핵을 안정화하는 안, 여러 작은 장치로 책임을 나누는 안, 주기적으로 쉬며 마력을 회복하는 안의 3개다. 모두 학교가 유지되는 동등한 엔딩이며 실패 엔딩을 숨기지 않는다. 선택에 따라 교정 장치 외형·수업 대사·후일담을 바꾼다. 별도 맵 세트를 만들지 않는다.

엔딩은 “학교의 시스템을 고쳤다”에서 끝나지 않고, 평범한 다음 날의 수업과 친구들의 모임을 보여준다. 플레이어가 돌아올 생활이 남아 있는 것이 감정적 보상이다. 엔딩 후에는 같은 저장에서 미완료 관계·프로젝트·선택 조사실을 진행할 수 있다. 최종 선택은 보관 저장에서 다시 볼 수 있고 이미 받은 보상을 중복 지급하지 않는다.

10. 학교 행사·동아리·작은 부탁

달력과 학기

20일 단위 계절 4개로 80일의 달력을 구성하고, 40일씩 두 학기로 표시한다. 시간이 오래 걸리면 다음 해 달력으로 계속 생활할 수 있다. 날짜는 풍경·계절 대화·보너스 재료·정규 행사 일정을 바꾼다. 메인 사건의 마감이나 게임오버는 없다. 1차 엔딩은 학교의 위기를 해결하는 시점이며, 반드시 80일째 졸업식으로 고정하지 않는다.

학기 시작에는 새 시간표와 관심 과목을 선택한다. 학기가 바뀌어도 미수강 수업은 복습 목록에 남는다. 정규 행사는 달력에 나타나고, 처음 놓친 경우 준비 모임·연습 회차를 예약할 수 있다. 행사를 매년 기다리지 않아도 주요 수작업 콘텐츠를 경험한다.

각 행사는 평균 24분을 목표로 한다. 행사 준비품은 기본 대여품을 제공하고 특정 프로젝트 완료를 필수로 하지 않는다. H04의 발표는 새 제작 과제를 강제로 추가하지 않고 기존 물건 또는 학교의 기본 시범 도구를 쓴다. 메인 사건 E와 미라의 관계 공연은 각각 이상 현상 해결과 개인 표현을 다루고, H04는 여러 학생이 모이는 발표회이므로 목표와 장면을 분리한다.

행사의 해금과 정규 개최일은 분리한다. 조건을 충족한 행사는 다음 정규 일정에 참가하거나 곧바로 연습 회차를 예약할 수 있다. 달력을 기다려야만 본문을 보는 일은 없다. 수업·행사·동아리·부탁은 각각 고유 완료 기록을 갖고, 다음 해에 재등장해도 최초 1회만 콘텐츠 수량과 시간에 집계한다. 핵심 체험이 80일을 넘겨도 달력은 순환할 뿐 콘텐츠가 복제되지 않는다.

동시에 두 사건이 같은 장소를 쓸 때

주요 사건 해결 연출→예약 관계 장면→예약 행사→평상 일정의 우선순위를 둔다. 여러 장면이 동시에 시작되지는 않는다. 먼저 끝난 뒤 나머지를 초대 목록에 남긴다. 가구 배치나 행사 소품은 원래 월드에 영구 덮어쓰지 않고 해당 장면의 배치로 구분한다. 사건 후의 영구 변화는 완료 상태에 따라 불러온다.

필수 의존 관계 점검

  • 사건 A–F는 공통 도입만 선행 조건으로 가진다. 다른 사건의 보상을 입장 키로 쓰지 않는다.
  • 각 사건의 A1→A2→A3 같은 내부 단계는 유지한다.
  • 수업의 응용 단계는 해당 기초 수업이 필요하다. 기초 수업은 복습으로 언제든 가능하다.
  • 관계 R1→R2→R3는 같은 인물 안에서만 순서가 있다. 필수 사건의 협조는 별개다.
  • 생활 프로젝트는 관련 수업 또는 관련 사건 발견 중 하나로 열고 두 조건을 동시에 요구하지 않는다.
  • 최종 실습은 A–F 완료만 확인한다. 수집률·친밀도·성적·날짜 조건을 숨기지 않는다.

수첩과 힌트

수첩은 오늘 일정, 사람, 사건, 주문 응용, 학교 기록의 다섯 탭으로 나눈다. 사건 항목에는 지금 아는 사실·현재 가능한 행동·필요 도구의 획득 방법을 보여준다. 미발견 정답을 체크리스트로 전부 공개하지 않는다.

힌트는 관찰 대상→도구의 성질→구체 행동의 3단계로 나눈다. 일정 시간 같은 방에 머물면 첫 단계 힌트를 제안하되 자동으로 정답을 말하지 않는다. 원하면 즉시 다음 힌트를 열 수 있고 보상을 줄이지 않는다. NPC에게 물었을 때도 같은 힌트 기록을 사용해 정보가 서로 모순되지 않게 한다.

마지막 단계 이후에도 어려우면 현장의 “교직원 도움 요청”으로 현재 방을 단계별로 함께 해결한다. 비용·친밀도·성적 조건과 보상 감점은 없다. 사건 전체를 자동 완료하여 단서와 내용을 건너뛰지 않고, 해당 방의 핵심 행동과 결과를 확인하면서 통과한다. 퍼즐 배치가 어긋난 경우에는 현재 방만 초기화할 수 있고 이미 얻은 단서는 유지한다. 이 지원도 저장·복원과 함께 검증한다.

마법 공통 규칙

Claude가 제안한 발사형·영역형·대상형의 3개 발동 틀을 사용한다. 주문은 이 틀에 사거리·대상·효과·비용을 지정한다. 대상에는 젖음·가연·식물·파손·공명·어둠·가동 같은 성질을 붙이고, 같은 성질은 생활 오브젝트와 적에서 같은 반응을 보인다. 모든 특수 상황을 개별 스크립트로 만드는 대신 공통 반응을 쓰고, 서사적으로 필요한 예외만 명시한다.

예를 들어 물결은 젖음 부여·씻기·냉각을 공통으로 제공한다. 화분에는 성장 준비, 오염물에는 제거, 과열 인형에는 약점 노출이 연결된다. 반응과 결과를 분리하면 한 주문의 조작을 새로 배울 필요 없이 다른 활동에 활용할 수 있다. 12개 마법×모든 물체의 무제한 조합을 약속하지 않는다.

이번 범위에서 보류할 것

멀티플레이, 모든 학년을 플레이하는 장기 캠페인, 결혼·가족, 완전한 자유 비행, 대형 농장 자동화, 직업 수십 개, 절차 생성 던전, 자유 전투 동료 AI, 생성형 무한 NPC 대화는 보류한다. 이 항목들은 재미가 없어서가 아니라, 학교의 일상·관계·마법 응용·자유 사건망을 먼저 완성하기 위해서다.

개발 순서 제안

  1. 핵심 체험 60–90분: 기숙사·교실·식당·저수로 일부, 주문 4개, NPC 3명, 사건 A의 두 해결 경로, 관계 사건 1개, 프로젝트 1개. “배워서 그날 써먹는 재미”와 조작·시간 부담을 검증한다.
  2. 자유 진행 4–6시간: 독립 사건 2개를 정방향·역방향으로 진행, NPC 6명, 일정·예약·저장·경제 복구. 전투를 선호하지 않는 유저도 완료 가능한지 확인한다.
  3. 전체 진행 골격: 6개 사건과 엔딩을 간단한 임시 화면으로 연결하고 모든 필수 의존 관계를 점검한다. 이때 40시간 콘텐츠를 모두 제작하지 않는다.
  4. 콘텐츠 확장: 검증한 틀로 수업·관계·조사실·프로젝트를 채운다. 새로운 시스템을 계속 추가하기보다 기존 장소와 사람의 반응을 완성한다.
  5. 전 구간 테스트와 정리: 시간 분포, 반복 피로, 빈 동선, 대사 모순, 엔딩 전 남은 활동을 확인하고 분량을 조정한다.

분량이 짧거나 길 때

실제 폭넓은 체험이 32시간 이하라면 먼저 빠진 콘텐츠와 단위 시간 가정부터 확인한다. 목표가 재미있는 짧은 체험인지, 내용이 부족한 체험인지 구분한다. 내용이 부족하다면 기존 권역에 서로 다른 문제를 가진 조사실·인물 후속 장면을 추가하고 예산을 다시 산정한다. 대사 속도를 늦추거나 작물 대기를 늘려 시간을 채우지 않는다.

44시간을 크게 넘으면 빈 이동·가방 정리·반복 채집·시간표 대기·연속 실패를 우선 줄인다. 이후 목표가 겹치는 작은 부탁을 통합한다. 관계의 중요한 전환이나 주요 진실을 먼저 잘라 결말이 갑자기 오게 만들지 않는다. 수량이 바뀌면 콘텐츠 상한 표와 시간 표를 함께 바꾼다.

중요한 위험과 대응

가장 큰 위험은 수업이 생활과 분리된 미니게임이 되는 것, 마법이 단순 문 열기 도구가 되는 것, 모든 자유 사건이 같은 형식으로 느껴지는 것이다. 이에 대한 첫 대응은 더 많은 시스템이 아니라 수업 직후 활용·대상 반응·사건마다 다른 문제 구조다.

두 번째 위험은 대체 해결 경로의 제작량과 검증량이다. 사건별 두 경로를 완전히 다른 이야기로 쓰지 않고 공통 현장·증거·후일담으로 합류시킨다. 세 번째는 NPC 12명의 깊이와 텍스트 규모다. 관계의 전환 36개와 변화가 남는 장면을 우선 완성하고 기본 인사의 양을 뒤로 둔다.
