# 프로그래머 관점의 구현 구조

작성일: 2026-11-02. 앞으로 구현할 구조를 정한 문서다. 현재 저장소에는 시스템 문서·예제·문서용 검증기가 있으며, 이 계획에서 말하는 Unity 게임 코드는 아직 없다. 아래 경로·클래스·메서드 이름은 구현을 위한 제안이다. 엔진 버전과 패키지 API는 기술 결정 작업에서 확정한다.

## 조립과 의존 방향

권장 배치는 향후 Unity 프로젝트의 `Assets/MagicCampus/` 아래다. 정확한 세부 경로는 Task 문서의 소유 범위를 따른다.

| 영역 | 책임 | 의존 가능 대상 |
|---|---|---|
| Contracts/Core | 타입 ID, 단위, 진단, Handle, 취소, 포트, 버전 계약 | 표준 C#만 |
| Content | 호출 파싱·형식/의미 검증·불변 Catalog | Contracts/Core |
| Domain | 상태 전이, 시간, 이동 의도, 거래, 마법, 이야기 규칙 | Contracts/Core, 검증된 콘텐츠 조회 |
| Application | 이벤트·예약·도메인 작업 조율, 트랜잭션, 안전 상태 경계 | 확정 포트와 도메인 |
| UnityAdapters/Presentation | 입력, 타일맵/충돌, 씬, 파일, UI, 카메라, 소리 | 위 영역의 포트 구현 |
| Bootstrap | 실제 서비스 생성, 의존 주입, 함수 핸들러 등록, 시작·종료 | 모든 모듈을 조립하는 유일한 위치 |

도메인은 Unity Transform, GameObject, 씬 이름, UI 컴포넌트를 저장하거나 직접 호출하지 않는다. 외부의 행동은 입력 명령으로 받고, 화면은 읽기 모형과 결과 알림을 받는다. 별도 에디터 프레임워크나 범용 게임 엔진 제작은 범위에 넣지 않는다.

## 상태와 쓰기 권한

`StateStore`는 영속 상태의 원자 교체와 revision을 관리한다. 각 서비스는 자신이 소유한 상태의 변경 계획만 만든다. 다른 서비스를 통해 가방·관계·완료 집합을 직접 수정하지 않는다. 트랜잭션 조율자가 각 계획을 같은 revision에서 검증하고 한 번에 적용한다. 실시간 위치·HP 등 휘발 상태의 전이는 지정된 시뮬레이션 단계에서 해당 소유자만 처리하며, 저장 시 안전 경계의 상태를 채택한다.

| 상태 | 유일한 규칙 소유자 | 영속/임시 경계 |
|---|---|---|
| 논리 위치·문·충돌 버전 | World/Movement | 안전 위치는 영속, 경로·이동 Handle은 임시 |
| 절대 게임분·잔여량·일 경계 | Clock | 시각·처리 원장은 영속, 정지 토큰은 임시 |
| 예약·초대 | Schedule/Reservation | 수락 상태는 영속, 자원 임대는 임시 |
| 물품·지갑·우편·대여 scope | Inventory/Economy | normal/grant와 거래 원장은 영속, loan은 scope overlay만 |
| 화분·돌봄·배치·설치 | Life/Placement/Project | 확정 상태 영속, preview·예약 재료는 임시 |
| 주문·고유 응용 상황·수업 | Ability/Class | 해금·상황 집합 영속, 투사체·쿨타임은 방 정책에 따름 |
| 적·퍼즐·임시 전리품 | Room/Combat | 미확정 overlay 임시, 확정 증거·열린 문은 영속 |
| 경험·관계·사건·증거·엔딩 | Relationship/Story | 공유 완료키·파생 상태와 함께 영속 |
| 읽음·힌트·설정 | Journal/Settings | 사용자의 선택만 영속, 조회 캐시는 재생성 |

원본 계약에 이미 저장 필드가 있는 경우 같은 필드를 재사용한다. 추가 필드가 필요하면 단독 계약 변경 작업에서 스키마·기본값·migration·정상/부정 예제까지 함께 정한다. 임의로 새 보조 플래그를 저장해 파생 상태와 어긋나게 만들지 않는다.

대여품과 대여품으로 만든 화분·먹이·가구는 과제 scope overlay에서만 유지한다. 영속 stacks/mail/plots/placements에는 normal/grant와 scopeId=null만 허용한다. 로드 후 대여는 현장에서 재수령한다. 지급 씨앗의 수확물, 지급 먹이의 수급, 지급 가구의 회수물에도 grant를 보존한다.

## 함수 호출 칸을 실행하는 방법

1. JSON 전체를 읽고 버전·닫힌 스키마를 확인한다.
2. 문자열을 따옴표·이스케이프를 인식하는 토큰으로 분해한다. 따옴표 안의 `/`는 명령 구분자가 아니다.
3. `functions.json`으로 함수 종류, 인자 순서/개수/타입, 기본값, 참조 종류를 확인한다. 위치 인자 뒤에 이름 인자가 온다.
4. 정의 칸에서 ID/방 목표 이름표/에셋 바인딩 색인을 유도한다. 별도의 중복 저작표를 만들지 않는다.
5. 가지 순환·미사용 가지, async 충돌·누락 await, 완료키·선행·출처·시간비용을 검사한다.
6. 유효한 전체 번들만 불변 Catalog와 타입 명령으로 공개한다. Runner는 문자열을 다시 해석하지 않는다.
7. 등록된 핸들러가 명령을 수행한다. `move`와 `perform`은 실제 성공까지 기다리고, `effects`는 script 전체 성공 후 원자 적용한다.

진단에는 파일, JSON Pointer, 엔티티, `event.snack#3` 같은 호출 위치, offset, 기대/실제값을 남긴다. 문자열 eval이나 리플렉션으로 임의 메서드를 부르지 않는다. 새 콘텐츠는 기존 함수를 조합하고, 새 행동 알고리즘은 함수 사전·실제 구현·검증을 추가한다.

## 커밋·실패·복원의 구체적 흐름

전경 장면: 조건 조회 → 같은 revision에서 재확인 → NPC/장소/입력/카메라 전체 임대 → 수락을 보존한 진입 안전 상태 → 이동·대화·선택·도메인 작업 → 결과/재료/비용 재검증 → 효과·완료·보상·시각을 함께 커밋 → 임대 회수 → 새 안전 상태. 실패·취소는 미확정 계획을 폐기하고 진입 상태로 복원하며 수락 초대는 남긴다.

실시간 방: 입장 체크포인트 → 적/퍼즐/임시 전리품 overlay → 방 목표 성공 → 짧은 전역 커밋으로 확정. reset은 현재 방의 미확정 상태만 버린다. 탐험 중 다른 곳에서 확정된 재배·구매·이전 방 증거는 보존한다. 전투 중 전역 롤백을 쓰지 않는다.

거래·선물·수확·제작: 견적/계획 생성 → 수량·출처·scope·공간·revision 재검증 → 소비·산출·우편·원장 함께 적용. 취소는 소비 0이다. 같은 transactionId/completionKey의 재시도는 재보상을 만들지 않는다. 대여 혼합 결과와 실패 반환에도 가장 제한이 강한 출처를 전파한다.

저장: 안전 불변복사 → 임시 세대 쓰기 → 체크섬 확인 → 이전 정상본 보존 → 교체. 오류는 메모리 성공을 보존하고 미저장 상태와 재시도를 표시한다. 로드에서는 버전·해시·migration·참조·불변식을 확인한 단일 세대만 채택한다. 구세대 지갑과 신세대 완료 원장을 섞지 않는다.

## 한 틱의 처리와 취소

입력/지난 완료 수집 → 정지 채널/시계/경계 처리 → 후보 조건과 전체 임대 → NPC 일정 의도 → Runner 명령 → 이동·충돌·전투·반응 → 발급 sequence 순 원자 커밋 → 임시 자원 정리·안전 상태·표시 갱신 순서다. 완료 통지는 다음 틱에 소비한다. 재진입 호출로 같은 틱 안의 처리 순서를 뒤집지 않는다.

Handle은 Pending → Running → Succeeded/Failed/Cancelled 중 하나로 정확히 한 번 종결한다. 취소는 반복 가능하며 자식 작업의 종결과 토큰 반환까지 소유자가 책임진다. async는 같은 목록에서 await로 닫고, 하나가 실패하면 형제 작업을 취소한다. Runner는 즉시 명령 64개 처리 후 양보한다.

시간 정지는 달력·평상 NPC/AI·플레이어·월드 시뮬레이션·장면 소유 연출을 구분한다. 메뉴 중에도 UI와 취소 입력은 처리한다. 달력이 멈춘 장면에서도 장면 소유 이동은 진행해야 한다. 자정은 새 교전을 막고 현재 작업의 안전 경계에서 귀환한다.

## 실제 구현을 시작하는 단위

첫 목표는 NPC 한 명을 초대하여 두 맵 사이로 이동시키고, 도착 후 대화·선택·효과를 진행한 뒤 저장·재실행하는 연결이다. 그 위에서 일정·대여·생활·마법·전투를 확장한다. 최소 연결 전에 40시간 분량의 콘텐츠나 전용 편집기를 제작하지 않는다.

각 Task 실행 시 읽을 원문, 직접 선행, 수정할 모듈, 입력과 결과, 실패·저장 정책, 완료 증거를 작업 카드로 제공한다. 같은 단계의 작업은 서로의 미완성 구현을 호출하지 않으며, 공통 포트와 공유 파일 수정은 앞선 단독 계약 작업 또는 뒤의 단독 통합 작업에서 한다. 테스트용 대역은 선행 계약에 맞춰 사용하되 실제 연결 검증은 단계 장벽에서 별도로 통과시킨다.

최종 보완 중 다음 규칙은 인수시험에 반드시 넣는다. 수업의 시간은 perform 결과에 담아 마지막 커밋에서 한 번만 가산한다. R2는 R1 이후 실제 참여한 서로 다른 두 유형을 세며, R1 이전에 해 본 활동에 재참여해도 인정한다. 평생 첫 유형의 +8 점수 원장과 혼동하지 않는다. 공격권 상한은 min(교전 설정, 프리셋 설정, 전역 3)이다. P07은 연금·요리 공용 시설이며 fine 판매 배율은 1이다. 사건 보상은 case.reward가 사건 정의를 읽어 노드 완료와 함께 한 번만 지급한다.

Task 완료는 코드 작성량이 아니라 명시된 인수 조건으로 판단한다. 증거는 contentHash·saveVersion·UnityVersion·초기 상태·입력 순서·trace·결과 상태를 포함한다. 문서 검사, 도메인 모델 검사, Unity 실행 검사, 사용자 플레이 검사는 각각 결과를 분리한다.
